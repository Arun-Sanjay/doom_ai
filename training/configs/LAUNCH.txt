Launching the unified run on the Linux box (96 worker processes x 12 environments, learner on CUDA)
==============================================================================================

Everything from the repository root on the box (/workspace/doom_ai), with the box's interpreter:

    PY=/opt/venv/bin/python
    CKPT=runs/combat_1/latest.pt        # the combat checkpoint to start from (any checkpoint of training.rl.train)

0. Once: the maps of the held-out gate (the frozen dev suites rebuilt as WADs; a second for both)

    $PY -m training.mapgen.cli --from-suite training/suites/dev_v1.jsonl     --out data/maps/dev
    $PY -m training.mapgen.cli --from-suite training/suites/dev_nav_v1.jsonl --out data/maps/dev_nav

1. Preflight, two iterations (about a minute): checks the teacher in the workers and the new log columns

    $PY -u -m training.rl.train --maps data/maps/train/manifest.jsonl --config training/configs/unified_full.json \
        --init $CKPT --workers 96 --envs-per-worker 12 --out runs/unified_preflight --max-iterations 2

   It must print, in this order:
     learner device: cuda (...)
     initial weights from runs/combat_1/latest.pt
       (before it, "WARNING: ... no provenance record" if the checkpoint was written before provenance records
       existed: nothing then checks that the current network and front end still compute what it was trained with)
     rollout: 1152 environments on 96 CPU worker processes, front end: doomnet, 1500 maps in tiers [0, 1, 2, 3, 4], 73728 steps per iteration
     teacher: real; labels on 919 of 1500 maps (...); beta 1 -> 0.1 over 30000000 steps
     it 1 steps 73728 stage nav | ... | beta 1.00 forced 0.5-0.7 agree ... CE ... field ...
   "forced" is below 1 at beta 1 because off-grid maps and steps with a visible enemy are never mixed.

2. The run

    mkdir -p runs/unified_full_1
    nohup $PY -u -m training.rl.train \
        --maps data/maps/train/manifest.jsonl \
        --config training/configs/unified_full.json \
        --init $CKPT \
        --heldout data/maps/dev/manifest.jsonl \
        --workers 96 --envs-per-worker 12 \
        --out runs/unified_full_1 > runs/unified_full_1/train.out 2>&1 &

    tail -f runs/unified_full_1/train.out            # one line every 10 iterations, held-out lines, resets
    # stop with a final checkpoint:   kill -TERM <pid of the python process>
    # continue after a stop or a crash: the same command with  --resume runs/unified_full_1/latest.pt  in place of --init $CKPT

   Unattended overnight: a failing environment is rebuilt inside its worker and a worker process that dies is
   replaced (columns env_resets and worker_respawns), so neither ends the run. What still ends it (the learner
   itself failing, or more worker replacements than the run allows) leaves latest.pt behind. This loop starts the
   run and resumes it from latest.pt after any abnormal exit; a SIGTERM to the python process ends the run cleanly
   (exit code 0) and the loop with it:

    ARGS="--maps data/maps/train/manifest.jsonl --config training/configs/unified_full.json --heldout data/maps/dev/manifest.jsonl --workers 96 --envs-per-worker 12 --out runs/unified_full_1"
    nohup bash -c "$PY -u -m training.rl.train $ARGS --init $CKPT || until $PY -u -m training.rl.train $ARGS --resume runs/unified_full_1/latest.pt; do sleep 30; done" \
        > runs/unified_full_1/train.out 2>&1 &

   (ckpt_NNNNNN.pt is kept every 25 iterations if latest.pt should ever be unusable.)

   Navigation only (tiers 0, 2, 3; no arenas): --config training/configs/unified_nav.json and
   --heldout data/maps/dev_nav/manifest.jsonl, same other arguments.

   Memory: 1152 engines at about 35 MB, plus 384 more for about two minutes during each held-out
   evaluation (every 150 iterations): about 55 GB at the peak. If that is too much, lower heldout_envs
   and heldout_workers together in the config (tolerance 0.06 assumes at least 384 episodes; use 0.08 for 192).

3. Columns of runs/unified_full_1/train_log.csv to watch (one row per iteration of 73,728 steps)

   throughput and health
     env_steps_per_s        the combat run made about 13,000; the labels cost a few percent of worker time (see
                            training/logs/unified_smoke.txt), so expect 11,000 to 13,000
     env_resets             rows restarted on a fresh map after an engine death or an exception (total of the run). The
                            first 20 are printed with their error. A handful per night is fine; a steady climb is not
     worker_respawns        worker processes replaced after dying; expected 0
     odom_errors            odometry updates that raised (pose kept). Was the cause of two crashes of the combat run.
                            Training keeps the pose and the map on such a step; submission/agent.py does not guard the
                            same call and clears its pose, map and recurrent state instead (measured: 22 free cells -> 0).
                            Until the agent does the same as training, every count here is a step the shipped agent
                            would handle differently from what the policy was trained with
     teacher_errors         internal errors of the teacher (that step is not labelled); expected 0
     kl, clip_frac, ev      PPO on the steps the policy chose itself (kl includes what distillation changes there)
     kl_unlabelled, minibatches
                            kl on the steps the policy chose itself that carry no controller label (fights, maps
                            without labels), manager choices included. About 6 in the very first update from a
                            combat checkpoint (the untrained target pointer is being rewritten), 0.01 to 0.03
                            afterwards. minibatches is 54 unless an update was ended early by a KL limit (none
                            is set; see "Starting from a combat checkpoint" in unified_nav.txt)
   the teacher terms
     beta, forced           beta falls 1 -> 0.1 over the first 30 M steps (about 40 minutes); forced follows it, scaled by
                            the share of labelled steps (column "labelled")
     loss_distill_heads     sum of the controller heads' cross-entropies; about 40 at the start from a combat
                            checkpoint (2.9 from a random start), falling to about 1.7
     loss_distill_subgoal   from about 2 to below 0.5
     loss_distill_target    from 8.3-8.8 (ln 4096 = 8.3) to below 2.5; the slowest of the three
     loss_field             about 18 at the start from a combat checkpoint (0.7 from random), falling to about 0.02;
                            field_rows is the share of manager steps it is applied on
     agree, agree_all       share of labelled head choices (and of whole steps) where the policy's most likely option is
                            the teacher's; agree_move / agree_strafe / agree_turn / agree_use per head. In the 25-minute
                            laptop run agree reached 0.81-0.82 on mixed trajectories within 80,000 steps and stayed there.
                            A health signal only, NOT the measure of imitation: the column is taken on the run's own
                            trajectories and falls as beta falls (0.83 at its best, 0.78 at the end at beta 0.2 in the
                            laptop run, where the final checkpoint scores 0.88 on teacher-driven states). Judge imitation
                            as in step 5
     agree_subgoal, agree_target, target_cells_off     the manager; target_cells_off should fall below 2 cells
   what the run is for
     heldout_exit_rate, heldout_episodes, distill_weight
                            every 150 iterations the policy alone plays 384 held-out episodes; the line
                            "held-out: exit rate X over 384 episodes (best so far B) -> distillation weight W" is
                            printed. W steps down only when X >= 0.3 (min_rate) and X >= B - 0.06 (tolerance), where B is
                            the best rate of any report that stepped W down: B never falls, so a rate that slides a
                            few points at every report stops the steps down once it is 0.06 below its best. Two
                            reports in a row below B - 0.06 step W back up one level. With a steady true rate W
                            reaches 0 after 5 reports at the median (7 at the 90th percentile; the reports are noisy)
                            and steps back up one level about once in 20 reports (simulated, see unified_full.txt)
     exit_rate_t0..t4       recent exit rate per tier in training (while beta is high this is mostly the teacher's)
     exit_rate_labelled / exit_rate_unlabelled
                            training episodes with and without teacher labels. The unlabelled ones (start off the grid)
                            are driven by the policy alone at every beta: the earliest sign that it navigates by itself
     kills, kill_frac, death_rate
                            combat must not be forgotten: kill_frac should stay near the combat run's level on the
                            tiers with monsters (the tier mix changes with the curriculum stage, column "stage")
     door_reversals         USE pressed twice on a rising door; should fall towards 0

4. After the run

    $PY -m training.rl.eval_alone --checkpoint runs/unified_full_1/latest.pt --maps data/maps/dev/manifest.jsonl --workers 16
    $PY -m training.rl.export runs/unified_full_1/latest.pt --dest runs/unified_full_1/policy.pt \
        --episode data/maps/dev/dev_v1_t2_000.wad
   export writes the agent's weights format and, with --episode, starts a real DoomAgent on the file (no untrained
   fallback) and plays one episode. Copy the file to submission/weights/policy.pt only after training/evaluate.py
   --compare says it is better than what is there.

5. Judging a checkpoint of the run (during it or after it; ckpt_NNNNNN.pt or latest.pt)

   Two measurements, both of the policy as the agent decodes it, both on held-out maps. Neither is a column of
   the training log (see "agree" and "exit_rate_t*" above for why those are not enough).

   a. Imitation, on states the teacher drives (16 workers x 10 environments x 256 steps):

    $PY -m training.rl.agree --checkpoint runs/unified_full_1/latest.pt --maps data/maps/dev_nav/manifest.jsonl \
        --beta 1 --workers 16 --envs-per-worker 10

      "agree" is the mean over the labelled head choices (move, strafe, turn, USE); "agree_all" the share of steps
      on which all four are the teacher's; agree_move / _strafe / _turn / _use the heads one by one. USE is "off"
      on most steps and lifts the mean, so read the per-head numbers and agree_all next to it. --beta 0 gives
      the same on states the policy drives itself into; that number is lower and is not the gate.

   b. The policy alone, per tier (2 episodes per map; no teacher, no mixing):

    $PY -m training.rl.eval_alone --checkpoint runs/unified_full_1/latest.pt --maps data/maps/dev_nav/manifest.jsonl \
        --episodes 2 --workers 16
    $PY -m training.rl.eval_alone --checkpoint runs/unified_full_1/latest.pt --maps data/maps/dev/manifest.jsonl \
        --episodes 2 --workers 16

      Read "tiers" in the output, one exit rate per tier, never the total alone: the total of a set moves with its
      tier mix, and a tier the run has not reached yet in its curriculum counts as a failure of the policy.

   Reference points, the 20-minute laptop check from a random start (tiers 0 and 2 only, 1.5 M steps; the gate it
   was built for is written out in unified_smoke.txt next to this file):
      a. 0.877 per labelled head, teacher driving (move 0.850, strafe 0.845, turn 0.816, USE 0.996); all four heads
         at once 0.626; student driving 0.726.
      b. tier 0: 0.78, tier 2: 0.51 of 120 episodes each on 60 held-out maps; tiers 3 and 4, never trained on: 0.20
         and 0.43 of 40 episodes each.
   The long run should pass both on every tier it has trained on. A checkpoint that scores lower on (b) than an
   earlier one of the same run on the same maps has lost navigation, whatever the training columns say.
